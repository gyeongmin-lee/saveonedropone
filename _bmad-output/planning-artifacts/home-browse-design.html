배경 및 목적

이 문서는 saveonedropone의 홈 화면(/)과 카테고리 페이지(/categories/[id])의 Browse 경험을 설계한다. PRD Epic 1(Public Discovery & Browse)의 Story 1.2, 1.3과 Epic 3(결과 화면)에 직접 영향을 미치며, Advanced Elicitation 및 Party Mode Review 세션(2026-05-10)의 결과를 반영한다.

설계 원칙

  • Occam's Razor: MVP 단계에서 알고리즘 복잡도는 데이터 가용성에 비례한다. 단순한 수동 큐레이션이 ML보다 낫다.
  • 소셜 공유 기반 발견: 이 플랫폼의 발견 구조는 개인화 알고리즘이 아니라 공유 링크 → 결과 페이지 → "More in [category]" 흐름이다. Browse는 보조 화면이다.
  • 마찰 최소화: 온보딩, 로그인 요구, localStorage 추적 없이 링크 클릭 즉시 플레이 가능해야 한다.

바이럴 루프 검증 질문 (MVP 통과 기준)

  • Q1: 스트리머가 같은 플랫폼을 2회 이상 방송에 사용하는가?
  • Q2: 한 번의 방송이 시청자 플레이 세션 1,000회 이상을 파생시키는가?
  • Q3: 결과 이미지 공유가 공유 링크 유입 세션 50회 이상을 만드는가?

⚖
홈 Trending 카테고리 캡 정책
동일 카테고리 브라켓은 홈 Trending에 최대 3개까지만 표시한다. 특정 카테고리 바이럴(예: K-pop 방송 후 급등, Reddit 유입 폭발) 시 홈 전체가 단일 카테고리로 도배되는 현상을 방지. 3개 초과분은 trending_score 순위에서 제외하되 해당 카테고리 페이지에서는 정상 노출. 전체 카테고리가 3개 미만인 경우(초기) 캡 미적용.

레이블 정책

레이블 단순화: 항상 "Popular Brackets" 고정

-- 레이블은 데이터 상태와 무관하게 항상 "Popular Brackets"
-- "Trending Now" 레이블 및 전환 로직 없음
-- 정렬은 데이터에 따라 자동 반영:
--   데이터 있음: trending_score DESC (카테고리 캡 3개 적용)
--   Cold Start:  is_curated DESC, created_at DESC

ORDER BY
  CASE WHEN trending_score > 0 THEN 0 ELSE 1 END,
  trending_score DESC,
  is_curated DESC,
  created_at DESC

"Trending Now" → "Popular Brackets" 전환 임계값 정의, 전환 타이밍 로직이 불필요한 복잡도. 레이블을 고정하고 정렬만 데이터 기반으로 작동시키는 것이 더 단순하고 신뢰성 있음.

태그 필터 UX CHANGED

⚡
태그 필터 UX — 서버 fetch + skeleton UI CHANGED
태그 선택 시 전체 페이지 리로드 없이 그리드 영역만 서버 fetch로 교체. skeleton UI로 로딩 상태 표시 → 체감 응답성 확보. URL은 /categories/kpop?tag=aespa로 자동 반영되어 직접 접속·공유 시에도 SSR에서 동일한 필터 결과 제공. debounce 150ms 적용으로 빠른 탭 전환 중 불필요한 요청 방지.

client-side 전체 로드 방식 제거 이유: 카테고리당 브라켓 수 증가 시 초기 로드 크기 상한을 정의할 수 없음. 서버 fetch는 확장성과 SSR URL 공유를 동시에 해결.
📌
태그 필터 적용 범위 — MVP: K-pop만, 이후 전 카테고리
MVP 단계에서 태그 필터는 K-pop 카테고리만 활성화 (['All', 'aespa', 'BLACKPINK', 'NewJeans', 'IVE', 'TWICE', 'ITZY', 'LE SSERAFIM', '(G)I-DLE', 'BTS', 'Stray Kids']). 다른 카테고리(Anime, Gaming 등)는 태그 필터 없이 탭(Popular/New)만 표시. 추후 각 카테고리별 태그 데이터 구축 후 전 카테고리 지원 예정. 카테고리에 태그가 없으면 필터 바 자체를 렌더링하지 않음.

알고리즘 확정안

Trending Score

-- Trending Score 계산
trending_score = plays_7d
              + (live_now_count * 10)
              + (share_clicks_7d * 5)

-- 갱신: 1시간 캐시 (Cloudflare Cache API)
-- live_now_count: live_sessions 테이블 active count JOIN (별도 인프라 없음)
-- share_clicks_7d: analytics_events WHERE event = 'share_click'
변수가중치선택 이유단계
plays_7d ×1 기반 신뢰도. 7일 window는 최근성과 안정성의 균형. MVP
live_now_count ×10 Maya에게 가장 의미 있는 시그널. "지금 스트리머 3명이 하는 브라켓" = 채팅 반응 보장. Epic 5 후
share_clicks_7d ×5 Q3 공유 루프를 Trending에 직접 반영. 공유가 많은 브라켓이 더 노출됨. Analytics 쌓인 후
제거: plays_1h × 10 가중치

방송 종료 직후 순위 급락 현상 유발 → 사용자 혼란. plays_7d가 충분히 최근성을 반영함.

live_now 데이터 소스

-- live_sessions 테이블 하나로 Trending + BracketCard 배지 모두 해결

-- Trending 집계에서:
LEFT JOIN (
  SELECT bracket_pack_id, COUNT(*) AS live_now_count
  FROM   live_sessions
  WHERE  ended_at IS NULL
  GROUP BY bracket_pack_id
) live ON live.bracket_pack_id = bp.id

-- BracketCard "🔴 Live 3" 배지: 동일 live_now_count 재사용

별도 실시간 집계 인프라 없음. live_sessions 테이블(Epic 5에서 생성) JOIN만으로 Trending 가중치와 카드 배지 모두 처리.

"More in [category]" 레일 구성 정책

항목결정
대상 브라켓 같은 카테고리의 trending_score 상위 (큐레이션 + UGC 혼합)
표시 개수 4개 (flex row) CHANGED
데스크탑 4열 그리드가 자연스러움. 기존 설계의 "가로 스크롤 3개" 방식 변경.
푸터 링크 "See all in K-pop →" → 카테고리 페이지 (Sam의 발견 경로)
UGC 포함 여부 포함. trending_score 기준이므로 자연스럽게 큐레이션 우세하지만 인기 UGC도 진입 가능.
현재 브라켓 제외 결과 화면을 생성한 bracket_pack_id는 레일에서 명시적으로 제외. 방금 플레이한 브라켓이 레일에 재등장하면 클릭 동기 없음.
✂
범위 외: 결과 페이지 URL 구조
session URL(/results/[sessionId]) vs canonical URL(/brackets/[id]) 결정은 MVP 구현팀에 위임. og:url은 C1 OG 스펙에서 "canonical URL 기준 권장 검토"로 명시.

결과 페이지 OG 메타태그 스펙 NEW

Discord · KakaoTalk · Reddit · Twitter 공유 시 링크 미리보기(OG 카드)가 Q3 유입의 실질적 동력. 동적 OG 태그 서버 렌더링 필수.

태그값비고
og:title [Champion 이름] wins [브라켓 이름]! 예: "NewJeans wins K-pop 4세대 아이돌 월드컵!"
og:image 챔피언 아이템 이미지 URL 브라켓 아이템 이미지 재사용. 최소 1200×630px 권장.
og:description [plays_count]명이 플레이했습니다. 당신의 선택은? plays_count = 해당 브라켓의 누적 세션 수.
og:url 결과 페이지 canonical URL session URL이 아닌 브라켓 URL 기준 권장 검토 (C3 이슈와 연계).
⚡
구현 노트
OG 태그는 SSR(서버 렌더링) 시점에 삽입되어야 함. client-side hydration 후 삽입하면 Discord/Slack 크롤러가 읽지 못함. Epic 3 Story의 SSR 요구사항으로 명시.

10

제거 결정사항 (Occam's Razor)

이하 항목들은 명시적으로 구현하지 않기로 결정한 것들이다. "나중에 추가하면 되지"라는 접근 방지를 위해 이유와 함께 기록.

For You 레일 + 온보딩 플로우

이 플랫폼의 발견 구조는 소셜 공유 기반이지 개인화 알고리즘이 아님. 이상형 월드컵(piku.co.kr) 등 유사 플랫폼은 For You 없이 성공. 주 진입 경로(Q3 공유 링크)는 홈을 거치지 않으므로 온보딩 완료율이 낮다. 개인화는 재방문 헤비유저의 니즈이며 초기 MVP 범위 밖.

New & Rising 탭

JTBD 불명확 — 탭을 "쓰는" 사람이 없음. "New"와 네이밍 혼동. MVP 기준 UGC 50개 미만이면 빈 탭. plays_24h 집계 파이프라인 등 숨겨진 기술 복잡도 존재. Tiermaker 등 성공한 유사 플랫폼도 2탭(Popular/New)으로 충분. UGC 발견은 New 탭 + "More in [category]" 레일로 대체.

localStorage (sodo:interests, sodo:play:*)

For You와 New & Rising 제거로 사용처 없음. 완주 이력 추적은 "완주"의 정의, 저장 시점, 만료 등 엣지케이스가 많음. 재플레이는 Q2(세션 수) 관점에서 오히려 긍정적이므로 완주 필터가 불필요.

Top All-time 탭

Popular이 높은 plays_7d를 이미 반영. 탭이 늘어날수록 인지 부담 증가. 초기 큐레이션 브라켓의 영구 상단 독점 문제 악화.

plays_1h × 10 가중치

방송 종료 직후 순위 급락 현상 유발. 사용자가 새로고침할 때마다 순위가 다른 것은 신뢰성 문제. plays_7d가 충분히 최근성을 반영함.

Rising decay 공식 plays_24h / sqrt(age_hours + 2)

New & Rising 탭 제거로 함께 불필요해짐.

Featured 섹션 (수동 큐레이션)

단일 브래킷이 홈 상단을 점유하면 해당 카테고리 팬에게만 유효하고 나머지 카테고리 팬에게는 노이즈. Q1/Q2/Q3 어디에도 직접 기여하지 않음. Trending의 Cold Start fallback(큐레이션 브래킷 우선 정렬)이 Day 1 앵커 역할을 대체. Weekly 수동 갱신 운영 부담도 제거.
